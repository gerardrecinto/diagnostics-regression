Which OS build got slower?

Devices send battery and speed numbers. This lab reads them with Spark, strips anything private, compares one build to the last, and files a bug once when a number got worse.

The pipeline

Five steps, each one tested

01

Ingest

Spark Structured Streaming. JSON in, Parquet out. Bad rows go to a reject table with a reason.

02

Privacy

Field allowlist, salted device token, no email stored. Tested.

03

Aggregate

Exact dedupe, then p50, p95, mean, std per build, app and metric. Groups under 20 devices are hidden.

04

Detect

Welch test plus a minimum effect, Bonferroni corrected. Improvements are never flagged.

05

File bugs

One issue per regression. REST API and Prometheus metrics sit alongside.

What each part shows

Real, tested, and where it stops

Streaming ingest

spark_jobs.py

Structured Streaming file source, checkpoint, micro-batches, foreachBatch sink. No Kafka here, see kafka-ops-lab. No Flink.

Data quality

test_pipeline.py

Every row accounted for: stored plus rejected equals read. Reject reasons kept.

Privacy

privacy.py

Allowlist, salted token, k of 20. Tests check no email and no device id in storage or the API.

Regression detection

regress.py

Two planted regressions and one change too small to count. Flags exactly the two.

Automatic bugs

bugs.py

Fingerprinted, filed once. The GitHub sink is tested against a local fake server, not against GitHub.

REST service

api.py

Validated query parameters. 200, 404, 422, 503 paths tested over HTTP.

Telemetry

deploy/

Prometheus metrics, five alert rules checked with promtool, a Grafana dashboard checked against real metric names. Never loaded into a live Grafana.

Airflow DAG

dags/

Three tasks, loaded and order-checked in CI. Never run under a live scheduler.

Scale

n/a

One machine, 45 thousand rows, about 40 seconds. Nothing here is a claim about billions of devices. Python and PySpark only, no Scala.

Decisions and trade-offs

Why this and not that

All design-only: nothing here ran in production.

Exact dedupe at aggregate time over watermark dedupe
WhyIn my run, rows older than the watermark vanished: one rejected row went missing, and a six-file test lost three. A test now pins it.
CostsA shuffle over the day's data.
Flip whenThe source is Kafka with a transactional sink, or ids live in a keyed store with a TTL.
Welch test on summary stats over raw events
WhyCost grows with groups, not events.
CostsMean is skewed for latency data. Fine at 1,800 samples, weak under a few hundred.
Flip whenSmall groups: Mann-Whitney or a bootstrap.
Bonferroni over Benjamini-Hochberg
WhyTwelve tests per build pair, and a false bug costs an engineer's time.
CostsMisses weak but real changes.
Flip whenHundreds of groups per build.
5% effect floor plus a test over significance alone
WhyAt large n a 0.5% shift is significant and not worth a bug.
CostsSlow creep under 5% per build goes unseen.
Flip whenAdd a trend check across several builds.
Salted hash token over raw device id
WhyDistinct-device counts still work for the k rule.
CostsRotating the salt breaks joins across periods.
Flip whenNever needed here. Keep the salt out of the repo in real use.
Fingerprint state file over searching issues
WhyWorks offline, no read permission needed.
CostsThe file must persist between runs.
Flip whenThe DAG runs on several workers. Search issues by fingerprint.
